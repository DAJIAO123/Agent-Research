# 当 Agent 走不通时：恢复能力比重复尝试更重要

## 摘要

失败是 Agent 进入真实环境后的常态。命令不存在、权限被拒、测试反复失败和文件被外部修改，都要求系统区分原因并保留可接手的现场。

## 先给结论

**恢复不是再试一次，而是分类、保存、换路和交接。** 可恢复的系统不保证每次完成任务，但要保证失败后状态仍然可读，已完成工作不会被误覆盖，下一步足够明确。

## 一、失败分类

- 输入错误：目标不清、参数缺失。
- 环境错误：命令、依赖、端口或服务不存在。
- 权限错误：能力或范围不允许。
- 工具错误：超时、崩溃、部分输出。
- 验证错误：实现存在，但不满足目标。
- 外部变化：文件、分支或服务在任务期间被修改。

不同分类需要不同动作，不能都交给重试。

## 二、中断与失败是不同状态

公开 Turn 状态区分 `Interrupted` 与 `Failed`。`turn/interrupt` 还要求精确匹配活动 Turn ID，并在 `TurnAborted` 后由客户端收到终态。

来源：[turn_processor.rs](https://github.com/openai/codex/blob/7b5b3bd5a2418a5e142449c9ab95e057d14bc98a/codex-rs/app-server/src/request_processors/turn_processor.rs#L1474)。

这让“用户主动停止”和“系统执行失败”不会混成同一种异常。

## 三、从代码到架构

rollout 重建器会识别 `TurnAborted`、`TurnComplete`、回滚和压缩边界，再重建存活历史。它的价值在于让失败现场可以被解释和恢复；成本是状态重放、旧版本兼容和陈旧状态处理。

简单的“保存最后一条回复”方案恢复快，却无法回答已经完成哪些动作，也无法保护部分修改。

## 四、实验：三种故障

设计一个任务，分别触发不存在的命令、被占用端口和权限受限路径。观察 Agent 是否：

- 给出不同的失败分类；
- 选择替代路径；
- 请求用户输入；
- 记录已完成工作和阻塞原因。

任务中途手动修改目标文件，验证恢复时是否重新读取而不是覆盖外部改动。

## 常见误区

- 不分析原因就重复同一操作。
- 遇到阻塞立即扩大权限。
- 恢复时依赖旧快照并覆盖新改动。
- 失败报告只写“未完成”，不留下证据和下一步。

## 本篇结论

失败恢复能力的衡量标准不是“永不失败”，而是失败后仍能让人理解现场、判断风险和继续工作。
