# 计划不是预测：Agent 如何让复杂任务保持可校正

## 摘要

复杂任务经常跨文件、跨工具和跨验证阶段。计划的价值不在于准确预测每一步，而在于把目标拆成可检查阶段，并在新证据出现后允许路径改变。

## 先给结论

**计划是协作和控制状态，不是模型内部推理的公开副本。** 它应该暴露目标、依赖、当前阶段和验收点，同时允许被工具结果改写。

## 一、四种东西不要混在一起

- 内部推理：模型生成判断的过程，不等于稳定的外部接口。
- 外部计划：给人和运行系统看的阶段状态。
- 工具事件：已经发生的动作和结果。
- 最终说明：对交付结果的总结。

公开协议中的 `ThreadItem::Plan` 被标记为实验性计划 Item。它证明系统可以把计划作为事件投影，但不能证明所有计划内容都代表模型内部推理。

来源：[item.rs](https://github.com/openai/codex/blob/7b5b3bd5a2418a5e142449c9ab95e057d14bc98a/codex-rs/app-server-protocol/src/protocol/v2/item.rs#L257)。

## 二、计划如何进入执行循环

```text
目标与验收标准
  -> 阶段拆分
  -> 当前阶段
  -> 工具动作
  -> 新证据
  -> 保持、调整或终止计划
```

如果测试发现接口与假设不同，计划应该更新，而不是强迫系统继续原路径。

## 三、从代码到架构

计划作为独立 Item 的好处是可观察、可更新、可被客户端显示。它的成本是同步：计划可能落后于实际工具事件，也需要兼容客户端对实验性字段的处理。

替代方案是只把计划放在自然语言中。这样实现简单，却无法稳定判断某阶段是否完成，也难以让人接手任务。

计划不应被设计成不可变脚本。Agent 的环境会变化，计划必须接受工具结果、用户 steer 和失败恢复。

## 四、实验：让一个假设失效

做两组任务：第一组只给目标，第二组给出阶段和验收标准。执行中让测试命令不存在或接口类型不同，观察：

- 是否重新定位问题；
- 是否更新阶段；
- 是否请求用户输入；
- 最终说明是否逐项对应验收标准。

这个实验测试的是计划的可校正性，而不是计划文本写得漂亮与否。

## 常见误区

- 把计划当成完整内部思维。
- 计划生成后不允许变化。
- 所有任务都强制生成长计划。
- 计划完成被误写成产品验证完成。

## 本篇结论

计划的工程价值是降低偏差的不可见时间，让人更早知道任务走到了哪里、下一步是什么、哪一个假设已经失效。
