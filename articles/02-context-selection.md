# 上下文不是仓库镜像：Agent 如何决定下一步看什么

## 摘要

Agent 面对的项目可能有成千上万个文件，但一次模型判断不可能无差别读取整个仓库。可靠性因此不只取决于上下文窗口大小，还取决于信息来源、优先级、按需读取和历史裁剪。

本文基于 `openai/codex` commit `7b5b3bd5a2418a5e142449c9ab95e057d14bc98a`，重点解释运行层如何在一个 Turn 中捕获 step context、从历史构造模型输入，并把工具结果放回下一次判断。

## 先给结论

**运行记录负责保留过程，模型上下文负责支持当前判断。** 两者不是同一份数据。上下文管理可以看成四个动作：发现可用来源、选择当前相关内容、按照模型限制裁剪、在证据变化后重新读取。

## 一、模型看到的不是整个仓库

当用户说“修复登录页问题”，可用信息至少有：用户要求、项目规则、当前文件、相关组件、测试结果、命令输出和历史修改。但其中只有一部分应该进入本轮判断。

如果把所有文件都塞进上下文，成本会快速上升，旧信息还会挤掉真正关键的约束。更合理的做法是让运行层保存完整现场，让模型在每一步获得与当前动作匹配的输入。

在 Codex core 的 Turn 循环中，`capture_step_context` 和 `clone_history().for_prompt(...)` 分别准备当前执行环境与模型可见历史。源码位置：[session/turn.rs](https://github.com/openai/codex/blob/7b5b3bd5a2418a5e142449c9ab95e057d14bc98a/codex-rs/core/src/session/turn.rs#L333)。

```rust
let sampling_request_input = sess
    .clone_history()
    .await
    .for_prompt(&step_context.model_info.input_modalities);
```

这段代码证明的是“模型请求使用经过处理的历史”，不能据此断言每个产品表面都采用完全相同的检索策略。

## 二、上下文有三个边界

### 资源边界

运行环境中能读取的文件，不等于本轮已经读取的文件。工具权限决定可触及范围，工具调用决定实际读取内容。

### 历史边界

Thread 可以保留较完整的历史，但 `for_prompt` 会按照模型输入能力和截断策略生成当前请求输入。历史记录和模型 prompt 是两个投影。

### 规则边界

项目级指令、目录级指令和用户当前要求可能共同影响任务。规则的加载范围和冲突优先级需要通过当前版本文档或实验确认，不能仅凭文件名推断。

## 三、从代码到架构

调用链可以概括为：

```text
用户输入
  -> TurnContext
  -> step context
  -> 历史 for_prompt
  -> 模型请求
  -> 工具结果写入历史
  -> 下一次 step context
```

架构上，集中构造上下文有两个收益：工具、模型和规则可以共享同一个 step 快照；一次判断不会同时使用互相矛盾的环境状态。代价是运行层需要处理裁剪、压缩、陈旧文件和长工具输出。

一个合理替代方案是让每个工具自行决定上下文，但这样会把规则、权限和历史选择分散到各个适配器，难以审计，也容易出现同一任务不同工具看到不同约束的问题。

## 四、实验：制造一条容易被忽略的规则

在临时仓库根目录和子目录分别放置不同的 `AGENTS.md`，让目标文件包含一个明显的约束，再要求 Codex 修改它。记录：

- 哪些规则被提及；
- 哪些文件先被读取；
- 工具输出变长后是否重新读取关键文件；
- 子目录任务是否遵循更近的规则。

实验不能证明所有版本的规则加载实现，但可以把“模型到底看见了什么”从猜测变成可观察问题。

## 常见误区

- 上下文窗口更大，就不需要选择信息。
- Codex 自动读取整个仓库。
- Thread 历史中的每个事件都会进入 prompt。
- 项目规则只是一段背景文字，不需要规定边界和验收。

## 本篇结论

上下文管理的核心不是囤积信息，而是让当前判断获得正确、及时、可解释的输入。运行记录越完整，越需要一个清晰的上下文投影层。
